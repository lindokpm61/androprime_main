### Before you write a status or a claim

Nine checks, all the same shape: verify the thing you are about to assert, rather than the document that mentions it.

- **Re-check documents this session CREATED, not only ones it changed.** A doc written mid-session records the world as of the moment it was written, including negative facts ("owed", "not built", "does not exist yet", "TODO", "blocked on"). The session then does some of that work, and the doc is now wrong in the most misleading direction: it understates progress and instructs the next reader to redo finished work. Grep the session's own touched files for those phrases and re-verify each. Do not exempt a doc from reconciliation because it is new — **recency is not currency**, and a doc is stale relative to the last write in its subject area, not its own creation time. (Observation 107.)

  **Grep for TWO families, because a doc rots in two independent ways that do not share a vocabulary.** Work-you-have-since-done, and facts-you-have-since-learned. A checklist grepping only the first will pass a document full of the second. Add the fact-not-known family: `unknown`, `not confirmed`, `unconfirmed`, `TBC`, `to be confirmed`, `could not see`, `not shown`, `not published`, `awaiting`, `need to check`, `check the`. And note the trigger: **whenever Keith supplies a document, export or dataset mid-session, re-grep the session's own files for the questions it just answered** — the arrival of data is the cue, not the completion of a task. Second-order damage worth avoiding: a stale unknown copied into outbound partner copy makes us look like we did not read what they sent. (Observation 328.)

  **Extend the re-check to every artefact the session PUBLISHED or updated, not only ones it created, and FETCH the published version rather than recalling that you updated it.** An artefact updated mid-session goes stale within the same session. Cheap mechanical test: grep the artefact for the ids or titles of work items completed later in the same session. For a published artefact the fetch is checking two things at once, since the local file and the published page also diverge if a publish silently failed. **Having updated something is the strongest reason to believe it is current and no evidence at all that it is.** (Observation 327.)
- **Any assertion of a CAUSE must carry its evidence grade in the same sentence — in STATE.md, and equally in a report, a chat answer or a recommendation list.** The rule was originally scoped to STATE.md; the same failure occurs in every user-facing surface, and those are where a wrong cause actually changes what someone does. "The thumbnail gate is the video arm's only blocker" was stated in two consecutive turns and put at the top of a recommendations list: 21 renditions did sit at `to-produce` all owing a thumbnail, but every one belonged to an asset still at `scripted`, nothing had ever been filmed, and a gate behind a step never taken cannot hold anything shut. One join against the parent status would have shown it. **Before asserting that X blocks Y, check the state immediately upstream of X** — a queue of items stuck at a gate is evidence about that gate only if the items reached it, and the most visible constraint is frequently downstream of the real one and looks identical from the queue alone. (Observation 223.) Either "verified" plus the query or artefact that shows it, or "inferred from the code, not yet confirmed against telemetry". The question to answer before writing: *what would falsify this, and did I run it?* A confident root cause reasoned from code once named two source lines and recommended a redesign; one read-only call against Sentry's tag breakdown showed the attributed page was 1 of 39 occurrences. A diagnosis and a hypothesis look identical once written down, and the cost of the omission is paid by whoever acts on it later. (Observation 139.)
- **When a fact lives in more than one store, "done" means every store.** Enumerate the stores for the fact being changed, write each, then **read each back**. A green checker defines the boundary of what "verified" means, and during a migration that boundary is narrower than the truth: a status change written to git and confirmed by the git-based scanner left the database holding the old value, which is what the live dashboard reads. (Observation 66.)
- **Never resolve a checker's finding by deleting the claim it checked.** Removing an assertion always satisfies a checker that verifies assertions, so "the finding went away" is not evidence the underlying thing is right — and a doc with nothing checkable left in it is unfalsifiable, which reads as clean. Classify first: **wrong value** (fix the value), **wrong claim** (fix the prose AND keep a correctly-phrased assertion), or **checker defect** (fix the checker, log it, leave the doc alone). If prose must lose an assertion, add a correct one in the same edit. (Observation 110.)
- **Before believing any zero, null, or "no change", demonstrate the instrument can produce the opposite — for a query of the SAME SHAPE.** A null result has two causes that look identical in the output: the thing is absent, or the instrument cannot see it. Only the second is a bug, and it is the one that produces the more publishable-looking number, because a clean zero reads as a finding while a broken instrument usually reads as an error. This inverts the usual defence: agreement with prior evidence raises confidence in a real measurement and says nothing whatever about a blind one. The rule generalises past deploy canaries to **any** reported measurement. Two sharpenings that are the whole value of it: the positive control must use the same operator, phrase structure and filters, varying only the term expected to differ, because **broadening a control makes it easier to pass and therefore weaker** — which is why controls drift toward uselessness without ever failing; and where the negative result would remove something from a list or close a line of work, require one **non-probe** confirmation (read the artefact directly) before acting, since a false negative there is silent and permanent. The diagnostic question is not "did the instrument respond?" but **"would this control have failed if my conclusion were wrong?"** A control that passes while testing an easier question is worse than no control, because it converts an unverified zero into a verified-looking one. Best of all, bake it into the tool: a tool printing its own sensitivity beside its result does not depend on the reader remembering this. (Observations 258, 261.)
- **A record is not read until its DISCUSSION layer is read.** Structured fields record what a thing WAS when it was filed; unstructured discussion records what happened to it. Every tracker, ticket and register has both layers, and the cheap, skimmable, authoritative-looking one is systematically the stale one, because updating a field is a deliberate act and leaving a comment is a natural one. So whenever a tracker id is used to support a claim about what is or is not decided, **fetch its comments in the same breath as its fields**. The reflex "I checked the system of record" is only sound if it names which layer was checked. Treat a **partial** record as a positive signal to dig, not a neutral one: a summary resolving one half of a two-part question is evidence the summary is lossy, not that the other half went unanswered. (Observation 266.)
- **Write a resolution into the artefact that RAISED the question, not only into the tracker and the register.** A question and its answer living in different documents is a guaranteed future false report. A record's specificity is not evidence of its currency, and the two are easily confused because staleness and reliability present identically: a dated paragraph naming exact ids and line numbers reads as authoritative precisely when it is most likely to have been overtaken. So the question to ask of any "still open" claim is not "is this well-sourced?" but **"what would have had to happen for this line to be updated, and did anyone have a reason to do it?"** Where a doc names an external tracker id, treat that id as a **required lookup before quoting the surrounding text as current**. And prefer the cheapest direct re-test over any record: for a copy removal, grep the string, because **the code cannot be out of date about itself**. (Observation 264.)
- **Flag any status value that cannot be shown false.** A status that cannot be falsified does not track work, it suppresses questions about it, and it does so most effectively for the work nobody wants to declare dead. The test for a status vocabulary is not whether each value is meaningful but whether each is **decidable**: what observation would show this to be false, and would anyone make it by accident? Prefer a value carrying its own expiry over one describing an intention — `active (last artefact: <date>)` rather than `ongoing`, so an empty directory or an old date renders the status visibly false without anyone investigating. Sweep for this at wrap: any status outside the closed checkable set, and any `active` whose stamped date predates the review interval. (Observation 262.)
- **Before recording or escalating anything as unconfirmed with an outside party, search the correspondence layer.** Three layers hold three different things about the same fact: the spec layer raises the requirement, the contract layer holds the obligation, and the **correspondence layer holds the answer**. Absence in the first two is not evidence of absence. A spec's bare "confirm against the lab's assay" was read as a live TODO when the partner had already confirmed it in writing three months earlier, filed one directory away — one step from emailing a slow-responding commercial partner to re-ask a settled question. Grep the counterparty's correspondence directory, and state the search you ran, so the negative is visibly established rather than assumed. (Observation 133.)

**This stage is the safety net, not the intended point of capture.** Keith's standing preference is that a doc describing code changes in the SAME change as the code (a middleware gate + its CONTEXT route-table row; a threshold + the STATE entry) — co-locating the edit is the cheapest defence against the CONTEXT-vs-live drift the repo's own conventions warn about. If wrap is finding un-synced docs at session end, they should have been synced at edit time; note them here but treat the pattern as a prompt to sync earlier next time. (Observation 4, 2026-07-25.)

A generic tool description and a local convention will eventually contradict each other, and the local one usually wins silently. **When a create succeeds but a downstream check disagrees, believe the check and go read its matcher** before assuming it is stale; this is the concrete case behind step 4's "exit 1 is never a pass", where exit 2 was correct and the instinct to trust three successful creates over it was the thing to resist. 4. **Then run the reconciliation, because the convention above is a promise and this is the control:**

   ```bash

   ```

   Read-only diff of both stores: in the log but not on the board, on the board but not in the log, duplicate tasks, and status mismatches. **Exit 0 agree, 2 drift, 1 could not run — and exit 1 is never a pass**, because a comparison that did not happen has cleared nothing. The convention already named this exact failure ("an entry in only one of the two is drift, and the drift is invisible from whichever side you happen to be on") and shipped nothing to detect it. (Observation 158.)

### Three-way ownership — file each learning by type, never twice

A single learning goes in exactly ONE of these. Do not duplicate across them.

- **Durable fact or preference** (a threshold, a business rule, a behavioural preference) → **memory** (`memory/`, if personal/behavioural/tooling) or the owning workspace **CONTEXT.md** (if business). Handled in Stage 1.
- **Dated live-status change** (deployed, approved, activated, signed-off) → the owning workspace **STATE.md**. Handled in Stage 1.
- **Skill-definition improvement** (a SKILL.md needs a new rule/enforcement, or a new skill is warranted) → a **task-observer observation**, surfaced here, applied later on review. NOT memory, NOT STATE.

Memory owns the *fact*. STATE owns the *status*. task-observer owns the *skill edit*. If a learning feels like it belongs in two, split it: e.g. "Keith wants docs synced when code changes" is a behavioural preference (memory) AND a candidate rule for the code-editing skills (task-observer observation) — the fact goes to memory, the skill-edit suggestion goes to the log.

## Stage 3 — Git

- Stage by explicit path only — NEVER `git add -A` or `git add .`.
- **Begin the staging call with `cd "$(git rev-parse --show-toplevel)"` in the same invocation.** The Bash tool's working directory persists between calls, so a repo-relative `git add` can resolve somewhere else and stage nothing, or the wrong thing. The cwd rule already in `andro-prime/CLAUDE.md` was written as "any search"; this hazard is not a search, and the wording is why it has now fired three recorded times while in context. The rule is **any command taking repo-relative paths, `git add` included**. A rule fixes a decision point; this hazard has no decision point, so it needs a command shape instead. When a documented rule is violated a third time while in context, the defect is the rule's scope or shape, not the reader's attention. (Observation 326.)
- **Never let a patch anchor span a newline.** This repo has mixed line endings, so any pattern containing `\n` carries an invisible assumption that is true for some files and false for others, and the same code then appears to work intermittently for reasons not visible in it. Choose anchors that sit inside a single line, such as a heading's text. Keep asserting the anchor's presence before writing, which is what converts a silent no-op into a loud stop. Where multi-line context is genuinely needed, **read with newline preservation, normalise to `\n` for matching, and write back in the file's own ending**:

  ```python
  raw  = open(p, encoding='utf-8', newline='').read()
  crlf = '\r\n' in raw
  s    = raw.replace('\r\n', '\n')          # match and edit on LF
  ...
  open(p, 'w', encoding='utf-8', newline='').write(s.replace('\n', '\r\n') if crlf else s)
  ```

  And note the diagnostic trap: **`cat -A` through a pipe is not a reliable line-ending check on this platform** — use a byte count in Python, or `git ls-files --eol`. When a string match fails against text you can see in the file, suspect the bytes you cannot see before suspecting the text; when checking an invisible property, verify the instrument is not itself normalising the thing being measured. (Observations 317, 341. Worth also adding to `andro-prime/CLAUDE.md`'s "Tool and platform facts", which is not done.)
- Only stage files this session actually created or changed. Look at the working tree first; if there are unrelated dirty files from another session, leave them and say so.
- **Every command in a staging sequence must have a reason you can state, and nothing speculative belongs in one.** A reflexive `git rm --cached <file> 2>/dev/null; git checkout -- <file> 2>/dev/null` appended to "tidy" something staged a deletion that the following `git checkout --` did not unstage, so the commit removed a deliberately-kept reference artefact from the repo. Both halves were stderr-suppressed, so neither could report having nothing to do. **Never suppress stderr on a git command that mutates the index**, and read `git diff --cached --stat` for unexpected `delete` entries before committing rather than skimming it for the additions you expected. A tidy-up command with no stated purpose has no expected outcome, so nothing about its actual outcome can look wrong. (Observation 197.)
- **For a known, small number of files, edit with Read + Edit, not `sed`/`perl`.** A hand-escaped `perl -0pi -e "s|…|…|"` — a long regex carrying `/`, `(`, `)`, `+`, `$`, `|` and `[]` through a double-quoted shell string against a slurped file — did not error: it **prepended** the replacement to line 1 and left the original untouched, corrupting two files identically and silently. A substitution that matches nothing and one that matches wrongly both exit zero, whereas Edit fails loudly on a missing target, which is exactly the signal a regex withholds. Where a stream editor is genuinely unavoidable, verify by reading a changed line back rather than trusting the exit code. (Observation 196.)
- Commit straight to main (no branches, no PRs for solo work), conventional-commit style matching repo history, e.g. `docs(products): ...`, `feat(content-engine): ...`.
- **Commit-message mechanics.** Use a POSIX heredoc — `git commit -F - <<'EOF' … EOF` — or a single-line `-m`. For large or quote-heavy messages, write the message to a file with the Write tool and `git commit -F <file>`. **Why, and the shell-dialect trap that makes it matter, is in `andro-prime/CLAUDE.md`** ("Tool and platform facts") — it was moved there because the mistake happens mid-session and this skill loads only at close-out, so the rule sitting here could only ever explain the failure, never prevent it. (Observations 11 and 113.)
- Push to origin main.
- **A push to `main` auto-triggers a Coolify build + deploy** (`andro-prime/09_website-app/deployment/coolify/deploy.md`) of every non-flag-gated change — so a push IS a deploy. Never report "nothing deployed" after a push, and never assert "deployed/live" without confirming it (both were wrong in the 2026-07-25 session, misleading Keith). **Distinguish "a deploy ran and contained no live-served change" from "no deploy happened" — only the first is ever true after a push.** This fact also lives in `andro-prime/CLAUDE.md`, because it governs every mid-session push and this skill loads only at close-out. (Observation 144.)

- **The guard against build-context breaks is structural, not a compilation.** The 2026-08-02 production break came from a static import reaching above `frontend/`. Coolify runs `docker build` with the context set to `frontend/` alone, so `COPY . .` never copies the repo-root file and the module cannot resolve inside the image. **Both `tsc` and a full local `next build` pass**, because both see the whole repo and the deploy image does not — so "run the build before pushing" would NOT have caught it. The actual guard is the assertion in `frontend/scripts/content-engine/test-content-doctor.ts` that no static import under `frontend/` resolves outside it, run on push by `.github/workflows/content-engine-ci.yml`. If this session added or moved an import that crosses a directory boundary, run `npm test` in `frontend/`. (Observation 124 and its correction.)

  **`npm test` is an `&&` chain, so name the sub-command for the area you changed as well.** Its first link is `typecheck:scripts`, and everything after it is unreachable if that link fails — a chained verification command fails as a unit, so any one broken link disables verification for everything downstream, silently, and the red output belongs to someone else. That invites the reader either to misattribute it or to learn to ignore it, which is worse than having no test. So: if it fails, establish whether it failed in **your** area before treating the result as either your problem or a pass, and invoke the specific suite guarding the changed code directly (`tsx scripts/test-content-doctor.ts`, `tsx scripts/test-classifier-regressions.ts`, and so on). Treat "the aggregate command does not currently run" as a finding to report at wrap, never a detour to work around silently. (Observation 168 — logged 2026-08-07 when the chain was failing on three pre-existing errors; re-tested 2026-08-15 and `typecheck:scripts` now exits 0, so the specific breakage is fixed and the rule is kept for the next time it is not.)

- **Verify the deploy after EVERY push. There is no docs-only exemption.** The old rule here skipped verification when no live-served surface changed, and it broke production the first time it was tested: **the build compiles more than it serves**, so a tooling script or a moved data file gets type-checked by `next build` and can fail the deploy with not one served byte changed. (Observation 123.)

  1. **Is the app up?** Fetch `https://andro-prime.com/`. **Not `/api/health` — that route does not exist** and returns 404, so the named-first check fails in exactly the way that looks like the outage it was meant to detect. (Observation 96.) And **a 200 is not deploy verification**: the previous build serves happily through a failed deploy, so liveness proves the OLD build is alive and says nothing about the new one. (Observation 123.)
  2. **Pick a canary that is capable of moving.** Ranked — take the highest available and **record which one you used**, so the choice is documented rather than improvised:
     1. **A per-run unique value** — build id, or a commit sha stamped at build time. Strongest, because it cannot collide with the old build.
     2. **Two-sided:** a string this session ADDED plus one it REMOVED. **Old-string-absent is the load-bearing half.** New-string-present alone gives false positives, because the old build may already carry that string in a shared component, meta tag or feature list.
     3. **Additive change — nothing was removed, so rank 2 is unsatisfiable.** Substitute proof of absence at the previous commit: `git grep -i '<new string>' <previous-sha>` returning nothing restores the property the two-sided rule protects, namely that presence cannot be explained by the old build. Do not silently drop to the one-sided check the rule warns against. (Observation 142.)

     Prefer a code-driven `app/*.tsx` page over a canonical-HTML-only change: it only changes after a full `next build`, so it also proves the build ran. (Observation 16.)

     Three rules govern which value you may use, and all three have already produced a wrong verdict:

     - **Never a content-addressed name.** `layout-<hash>.js` and every other chunk filename is a hash of its own source, so it is *engineered* to hold steady when source is stable. A docs-only or asset-only push produces a byte-identical name after a completely successful rebuild, and a monitor armed on it reports "no new build" as a guarantee rather than as a reading. Use the per-run build id instead — Next.js emits it in the RSC payload as `"b":"..."` and regenerates it every build regardless of whether any source changed. (Observation 212.)
     - **The canary must live in the same layer as the change.** A server-only module never enters a client chunk, so client-side fingerprints are structurally blind to it: one such probe sat unchanged through ten polls across five minutes while the deploy had in fact landed. Ask which layer the change lives in before choosing the signal, and for a server-side change prefer a request that exercises the new behaviour end to end — on a route nobody depends on, if a live surface would be at risk. (Observation 219.)
     - **Both operands must pass through the same extraction.** Capture the baseline with the *identical command* that will poll for the new value, never by hand and never from an earlier note. A one-sided normalisation is invisible, because a mangled id still looks like an id: `tr -d '<!->'` reads `!->` as an ASCII range and strips every digit, so the stored raw baseline could never equal the digit-stripped poll and the very first read reported the deploy complete twenty seconds after the push, two minutes early. Cheap check before trusting the instrument: run the extraction twice against the current page and assert the two agree. Note the direction — this is a false POSITIVE, which ends verification rather than prolonging it, and is therefore worse than the unchanged-probe case below. (Observation 242.)
  3. **Before reporting a canary as unchanged, prove the probe could have changed.** An unchanged probe has two indistinguishable explanations — the deploy did not land, or the probe is structurally incapable of moving. A build-timestamp poll once ran for thirteen minutes against a byte-identical asset whose mtime the bundler had preserved, and reported a successful deploy as failed; ten of the other eleven assets had already flipped. **A negative observation is only as strong as the instrument's ability to have produced a positive one** — sample a second independent signal before calling a deploy failed. (Observation 124.)
  4. **Match case-insensitively** (`grep -i`, or lowercase both sides): text rendered uppercase via a CSS `text-transform`/`uppercase` class still reads as the AUTHORED casing in the HTML source, so a case-sensitive match on the on-screen form silently misses and reports a false failure. Match the source string, not the visually-styled form. (Observation 19, 2026-07-25.)
  5. **The live page is authoritative. Build metadata is corroborating at most.** Sentry's releases endpoint returned the PREVIOUS commit for eighteen consecutive polls over nine minutes while the site was already serving the new build — the release row is written by the sourcemap-upload step, a different event that can lag the deploy, be skipped, or fail without affecting it. Its failure direction is the non-obvious part: **FALSE NEGATIVES**, so its absence proves nothing and only its presence is informative. Never report a deploy failed on build metadata alone. (Observation 141.)
  6. Report one of FOUR states explicitly: **verified live** (the canary flipped) / **build in progress** (canary not flipped yet — give the exact re-verify command and offer to poll again before ending; **poll on the CONJUNCTION — new string present AND old string absent, on every surface being checked — never on old-absent alone.** An absence test passes both when the thing you want has arrived and when *nothing* has arrived, so it cannot distinguish "replaced" from "momentarily empty", and mid-deploy a transitional response satisfies it vacuously. Any verification built on a disappearance needs a matching appearance to anchor it, or its success state includes the null state: a check whose passing condition can be met by the system serving nothing is satisfied most easily at exactly the moment the system is least healthy. Requiring two consecutive agreeing samples also suppresses this. Old-absent remains the half that rules out the previous build; it is simply not sufficient on its own. The per-run unique value has no such flaw and stays the strongest rung. (Observation 307.)) / **possibly failed** (still not flipped after several minutes, **and only after step 3 has cleared the probe itself** → tell Keith to check the Coolify dashboard) / **no served change was possible** (see below). Never leave deploy state unstated or guessed.

     **The fourth state is decided BEFORE polling, not after.** The canary ladder assumes every push can in principle change the served output. A commit touching only paths outside the image's build context breaks that assumption at the root: the build inputs are byte-identical, layer caching can legitimately return the same image with the same per-run build id, and no string can appear or disappear because nothing served was rebuilt. Following the ladder honestly then walks slowly toward "possibly failed" on a push that could not have changed anything and did not need to. Decide it mechanically — `git diff --name-only <prev-sha> HEAD` and check whether any changed path is under `frontend/` — and when none is, say so and stop, having confirmed only that the site is still up on the expected build.

     **There is a THIRD case, inside the build context but feeding nothing served**, so sharpen the test in two steps rather than one. First the intersection above: no `frontend/` path at all → state 4. Then, when there is one, ask whether the changed paths are **runtime-read**. Keep a short list of in-context-but-not-served paths in `09_website-app/CONTEXT.md` — today `content/blog/**` as the DB mirror, and `scripts/**` except where a build step imports them — and treat a commit touching only those as state 4 as well, owing liveness plus the reason rather than a canary. Corollary the wrap rules already imply elsewhere: **when the session's only served change is database-driven, the deploy canary is the wrong instrument entirely** and the verification is the served-page both-sides check from Observation 84. The general shape: a test standing in for a question must be checked against the question when it is first REUSED, not only when it fails. "Is the path in the build context" and "can the output change" agree almost always, and the gap between them is invisible precisely because the test normally gives the right answer. (Observation 320.) This sharpens the no-docs-only-exemption rule rather than reversing it: the thing owed for an out-of-context commit is liveness plus the intersection test, not a canary that cannot move. And note that step 3's remedy (sample a second signal) cannot rescue this case, because NO signal in the served output can move. (Observation 243.)
  7. **A deploy is not a flag flip. If the shipped change is gated behind a runtime env var, the canary above proves nothing** — it proves the code shipped, while the behaviour stays off because the running container never got the variable. Add a SECOND canary that exercises the gated behaviour itself (hit the route, read the rendered output, check the flag's observable effect), and report code-shipped and behaviour-live as two separate states. Coolify env changes need a container restart to take effect, so "I set the variable" is not "the variable is in the process". (Observation 29.)
  8. **Content served from the database is not covered by the deploy canary at all.** Blog article bodies live in `blog_articles.body`, not in the built bundle, so a copy fix is live or not live independently of any build. Verify those by fetching the served page and checking both sides (old string absent, new string present) after calling `/api/revalidate` with the slug. See `publish-article` for the full rule. (Observation 84.)
- **Code first, verify, then content. Never the same step.** Any content held in the database, a CMS or a content store that names a symbol, key, component or prop introduced by the same change must ship AFTER the code that provides it, as a second step. The database write is instant and the deploy is not: a config map gained a new key while an article body was updated in the same breath to reference it, the running build had no such key, the resolver threw at render, and a published page returned 500 until the body was reverted. The reverse ordering is free — with the code deployed first the old body keeps working, and the body switch afterwards is a no-risk write. Order the two writes so every intermediate state is valid on its own: the slow store first, while the fast one still describes the old world. (Observation 219.)
