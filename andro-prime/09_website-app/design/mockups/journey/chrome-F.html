The third one is deliberately unstyled and the frame set should say so rather than be silent. global-error.tsx renders its own bare <html> because it is the last resort for a failure in the ROOT LAYOUT ITSELF: at that point the fonts, the tokens and the nav are all suspect, so it can rely on none of them. What this file settles, and the three things it hands back. It closes the gap Keith found and the ten more the sweep behind it turned up, so the journey record now covers the pages AND the things on every page. It hands back three items that are not design questions. One is now answered: results-F.html section 08 drew a footer with four links on a layout that renders no footer, and Keith kept it (2026-08-29), so the authenticated area gains a footer it does not have today and that file now marks it as a proposal, distinguishes the two links with no page behind them, and reduces "Delete my results" to "Request erasure". Two: the /auth/* routes have no nav and no footer at all, and no frame states it, so a rebuild would probably add chrome that is currently absent. And three: five components have zero references anywhere (TrustBar, BiomarkerPanel, KitCard, SubscribeButton, AppPlaceholder) plus an empty components/lp/, which is a cleanup commit rather than a frame.

And one rule, which is the only thing here worth carrying to the next inventory. Enumerate the LAYOUTS, not only the pages, and take the layout list from the framework's own composition mechanism rather than from the route list. Each distinct layout is at least one frame, and the number worth writing down is layout to route-count: one footer frame carries 25 routes, which is more reach than any page frame in the entire set. Then run it backwards as well: for every frame drawn, confirm the component it depicts exists, because a route-based lifecycle check says nothing about a component that was drawn and was never real.
