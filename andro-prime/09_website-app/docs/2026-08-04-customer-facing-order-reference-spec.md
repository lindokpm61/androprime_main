## The problem

`kit_orders.id` is a UUID. It is the right primary key and should stay. It is the wrong thing
to read down a phone, quote in a support email, or write on a Post-it. The t01 order-confirmed
template puts it in front of the customer as their only reference:

```html
line 46  Order ref: {{ event.order_id }}
```

## Options considered

| Option | Verdict |
|---|---|
| **A. Derive a shorter number from the UUID** | **Rejected.** Any compression either collides or is still long, and it carries no ordering. All of the cost, none of the benefit. |
| **B. Own short reference, new column** | **RECOMMENDED.** Short, sortable, searchable, lab-independent. |
| **C. Show Vitall's `vitall_order_id`** | **Rejected, two reasons below.** |

### Why not Vitall's number

1. **It does not exist yet when the email fires.** The `purchase` event is emitted the moment
   the `kit_orders` row is inserted (`app/api/webhooks/stripe/route.ts` ~line 322). The Vitall
   dispatch is a separate fire-and-forget `fetch` made afterwards (~line 490), and
   `vitall_order_id` is only written when that call returns. Using it would mean either a blank
   merge field or deliberately delaying the confirmation email behind a third-party API call.
2. **The lab is expected to change.** `05_partners` targets disintermediation to TDL in roughly
   18 months. Customer references built on Vitall's IDs become meaningless on switch day, and
   until then we would be printing a competitor's identifier on our own receipts.

`vitall_order_id` stays exactly as it is: the internal key for talking to Ben. It is not
customer-facing.

## Recommended design

Three identifiers, each used by whoever it is for:

| ID | Audience | Example |
|---|---|---|
| `kit_orders.order_ref` | **The customer** | `AP-10042` |
| `kit_orders.id` (UUID) | Our systems; sent to Vitall as `partnerOrderId` | `1b429c90-...` |
| `kit_orders.vitall_order_id` | Vitall / Ben | `322947256` |

### Schema

```sql
alter table public.kit_orders
  add column order_seq bigint generated by default as identity (start with 10000);

create unique index kit_orders_order_seq_key on public.kit_orders (order_seq);
```

Render as `AP-{order_seq}` in the application layer rather than storing the prefix, so the
prefix can change without a data migration.

**Why start at 10000:** a sequence starting at 1 tells customer number three that they are
customer number three. Starting at a non-zero base obscures order volume without pretending to
be secret. Standard practice; do not over-engineer it into a random code, because the whole
point is that it is short and readable.

### Application changes

1. Emit `order_ref` alongside `order_id` on the `purchase` event.
2. Change t01 line 46 to `Order ref: {{ event.order_ref }}`.
3. Surface it on `/order/confirmed`, which **currently displays no reference at all** (verified
   2026-08-04: the page reads `session_id` from the query string and renders nothing from it).
   A customer who closes the email has no way to find their reference.
4. Make it searchable in whatever support surface exists. **There was none: `/admin/dashboard`
   carried cash position and gate metrics only, with no way to look up an order by anything.
   Built 2026-08-04** (`lib/admin/findOrders.ts`), searching by reference, customer email, or
   Vitall order id, with the field inferred from the shape of what is pasted in.

### Backfill

Three rows exist. An identity column assigns values to existing rows on add, ordered
arbitrarily; set them explicitly by `created_at` so the sequence matches purchase order.

**Note that all three existing rows are internal test orders, not customers:**

| `vitall_order_id` | Date | Status |
|---|---|---|
| `322942444` | 2026-06-25 | cancelled |
| `322942529` | 2026-06-25 | dispatched |
| `322947256` | 2026-08-04 | dispatched (Keith's Kit 1 process test) |

**Both done 2026-08-04.** `is_test` was added in the same pass (`20260804_kit_orders_is_test.sql`)
and is true on all three rows; every KPI view now filters it out, taking
`v_gate_tracker.total_kits_sold` from 2 to 0. The three test rows hold `order_seq` 1, 2, 3 and the
live sequence restarts at 10000, so no real customer is handed a reference that reads like a test.

## Not in scope

Changing `kit_orders.id`. The UUID is correct as a primary key and is what Vitall already holds
as `partnerOrderId` for the orders placed to date. Changing it would break the link on every
existing order.
