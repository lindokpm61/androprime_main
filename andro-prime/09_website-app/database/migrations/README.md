# Database migrations — canonical source

**Canonical migration source.** Migrations in this directory are the source of truth.

The `09_website-app/supabase/migrations/` directory is a build artifact synced from here by `frontend/scripts/sync-supabase-migrations.ps1` whenever `npm run db:push` or `npm run db:start` is invoked. The build-artifact directory is gitignored (see `09_website-app/supabase/.gitignore`).

**Add new migrations here only.** Do not hand-edit files under `supabase/migrations/` — they will be overwritten on the next sync.

## Conventions

- Filename: `YYYYMMDD_short_description.sql` — lowercase, snake_case, date prefix sorts chronologically.
- One transaction per file (`begin;` / `commit;`).
- Migrations are applied in filename order.
- A migration must be idempotent where practical (`create table if not exists`, `drop policy if exists`, etc.).
- **Every file here must be staged into git in the same commit as the change it supports.** This repo stages by path (`git add -A` is forbidden), so an applied-but-untracked migration is the likely omission, not a remote one: it exists in production and in your working tree while the record of it exists nowhere. `test-content-doctor.ts` fails if any file in this directory is untracked.
- **A superseded migration is corrected by a NEW file, never by editing the applied one.** Rewriting a file that has already run hides the fact that it ran in its weaker form. Put a `SUPERSEDED BY <file>` line in the old file's header and in the section it applies to, and name the superseded version in the new file's header.
- **Backfilling a new identity column takes two passes, not one.** `add column ... generated by default as identity` assigns `1..N` to the existing rows the moment it runs, in arbitrary order. A backfill that then writes the same range in the order you actually want collides against the unique index, because Postgres checks uniqueness row by row rather than at end of statement. Park the values somewhere free first (the negative range works and needs no extra column), then assign the real ones. See `20260804_kit_orders_order_seq.sql`. Related: `restart with N` moves a sequence's current value but leaves `start_value` untouched, so pin the floor with `set start with N` too if a later bare `restart` would land somewhere harmful.
- **The applied-migration ledger can hold more entries than this directory holds files, and the difference must be written down.** A draft that was superseded within the same session leaves a ledger row with no file (see `20260801_content_state_guards.sql`, which is one file and two ledger entries). Record it in the surviving file's header, so a reader counting one against the other is not left to re-derive it.

## The snapshot lives next door, and it is what you rebuild from

**`../schema/baseline-2026-08-14.sql`** is a full `pg_dump --schema-only` of the `public` schema. It is
the artefact to rebuild an empty database from, and the answer to a real gap: before 2026-08-14 the
schema existed only inside the live database. Eleven ledger entries had no file here, nine files here
had no ledger entry, and the project had no managed backup, so losing the database meant losing the
definition of it.

**This directory is the LOG. That file is the SNAPSHOT. They are not interchangeable.**

- Rebuilding an empty database: use the baseline, then apply only the migrations dated after it.
- **Never replay this whole directory against a live database.** Some files here are not safe to
  re-run: `20260804_kit_orders_order_seq.sql` says so in its own header, because its closing
  `restart with` would reissue order references customers already hold.
- The baseline is deliberately NOT in this directory. `sync-supabase-migrations.ps1` copies every
  `*.sql` here into the Supabase CLI's migrations directory, where `supabase db push` would apply it
  on top of an existing database. A snapshot in an ordered log is a trap, not a record.
- Regenerate the baseline after any schema change worth checkpointing. The exact command, and the
  connection caveat (session pooler on 5432; the direct host is IPv6-only), are in the file's header.
